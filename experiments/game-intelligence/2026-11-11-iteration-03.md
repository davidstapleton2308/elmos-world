## Reproduced scanner completeness bug

Tested a direct reproduction of the production `_walk` loop on a disposable directory with 1,801 empty flat files. Production logic returns `(files=1800, dirs=0, truncated=False)`: the inventory is incomplete but is represented as complete. A corrected prototype tracks an explicit `hit_limit` and returns `(1800,0,True)`. This is a scanner-logic reproduction, not a full production import. The issue arises because the code uses `bool(queue)` to report truncation; if the last processed directory is the root, the queue is empty even when there are unexamined entries. A folder containing 1,800 benign files followed alphabetically by a malicious link, incomplete transfer marker, or relevant executable can evade the inventory's completeness checks. `candidates()` has a separate unbounded walk, which may then inspect files absent from the safety inventory.

### Patch design
Use a shared bounded inventory for *all* evidence and candidate selection, with explicit status: `complete`, `entry_limit`, `depth_limit`, `permission_error`, `reparse_point`, `changed_during_scan`. Any non-complete status blocks automatic moves. Explicitly detect whether more entries remain before reporting complete. Do not skip a protected subdirectory without marking it as intentionally excluded from the evidence and the move safety policy; a directory that is moved wholesale still carries its excluded contents.

## Additional finding: skipped directories still move
`_walk` skips `mods`, `tools`, `patch`, `fix`, etc., but `move_verified` renames the *entire* folder. Thus an uninspected symlink, transient download or unexpected executable inside an ignored directory could be moved despite a 'complete' safety scan. The fix is a **two-pass inventory**: all descendants for safety, selectively scoped descendants for game evidence. No ignored directory is ignored for filesystem integrity. Reparse points and transient files anywhere block automatic moves.
