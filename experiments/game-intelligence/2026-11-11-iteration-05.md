# Game Intelligence Lab — 2026-11-11, iteration 5

## Source verification
Read `app/smart_discovery.py` on main (blob `e0fc204f7d022af6eef746e73c2f5d538befe22b`) and prior iteration 4. Current `scan_downloads` and `discover_emulators` use a fixed alphabetically sorted first 200 entries. The proposed recency-first workaround is not sufficient to guarantee eventual discovery.

## Hypothesis
A bounded, persistent queue of discovered entry identities will avoid starvation under directory churn better than repeatedly scanning the alphabetical or newest 200 entries. A naive numeric round-robin cursor over a newly sorted list may still skip entries when names are inserted, removed or renamed.

## Disposable simulation
Used 10,000 synthetic entries named A_00000..A_09999 and one late-sorting game Z_NEW_GAME, batch 200, 60 cycles. After the first cycle, each cycle deletes one early entry, renames one existing entry, and adds two entries. All simulated in memory; no actual games or Downloads touched. No real executable or ROM used. Each algorithm receives the same mutations and 200-entry budget per cycle (queue algorithm can skip deleted entries).

Results:
| Algorithm | First discovery of Z_NEW_GAME | Distinct entries inspected over 60 cycles | Final extant entries never inspected |
| --- | ---: | ---: | ---: |
| Fixed alphabetical top 200 | Never | 259 | 9,860 |
| Recency-first top 200 | Cycle 1 | 318 | 9,742 |
| Numeric round-robin over re-sorted list | Cycle 51 | 10,069 | 107 |
| Stable snapshot queue plus appended changes | Cycle 51 | 10,176 | **0** |

The snapshot queue inspected 10,176 live candidates while the other algorithms each selected 12,000 candidates including repeats. The snapshot queue is a model of a durable worklist, not a tested Windows USN implementation. Results are deterministic for the supplied synthetic workload; they are not production game-classification or artwork accuracy metrics.

## Novel finding
A numeric offset is not a durable cursor in a changing sorted directory. Insertions/deletions ahead of the cursor shift its meaning, so it can skip candidates even after enough scan budget has passed. This experiment exposed 107 such missed final entries in the naive round-robin implementation. A persistent queue with stable identity and an append-only change feed avoids this particular problem.

## Proposed implementation
1. Create a SQLite `discovery_jobs` table with stable volume/file identity when available, normalized path fallback, generation, first_seen, last_seen, state, retry_at and scan_version.
2. Initial full enumeration queues every eligible entry. New/renamed files enqueue via ReadDirectoryChangesW or periodic reconciliation. Process a fair bounded batch, not only the most recent entries; reserve capacity for old work.
3. Persist checkpoints transactionally, and periodically reconcile the filesystem to recover missed events, watcher overflow, reboots, and removable-drive disconnects.
4. Distinguish enumeration completeness, classification confidence and move authorization. Never interpret 'not seen in current batch' as absent.
5. On Windows, handle hardlinks, junctions, reparse points, file-ID reuse and permissions explicitly; the in-memory test does not validate those cases.

## Limits and next experiment
No GitHub application code modified. This simulation tests scheduling/coverage only, not actual filesystem watcher reliability, game identity, emulator detection, artwork correctness, classification precision/recall, move false positives or runtime latency. Next: build a disposable Windows filesystem integration harness with SQLite persistent jobs, restart/recovery tests, symlink/junction cases, watcher overflow, and a 200-item-per-cycle budget. Also test dual queues (fresh and backlog) under sustained high-rate arrivals to guarantee no starvation.
