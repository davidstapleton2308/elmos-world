## New hypothesis: classification score must not authorize mutation

A high score from **self-asserted, correlated** signals (matching folder/EXE names, UnityPlayer.dll, *_Data directory, a manifest filename) is not proof of the claimed product. Emulator filename plus config filename is equally spoofable. In current code `_emulator_signature` awards 78+8+18 = 104 (capped 100), so a counterfeit emulator-like package could be auto-ready. `_steam_manifest` counts manifest filenames, not validated product provenance. `inspect_manifest_names` accepts syntactically plausible self-authored names, which are useful hints but not verified identities.

Proposed **two-key gate**: score only ranks review candidates. Automatic move requires (1) high-confidence classification and canonical identity based on a separately verified anchor (for example, known signed game binary or a store ID cross-checked with a trusted installed storefront record) and (2) filesystem integrity/transaction authorization. Unknown preinstalled games remain in review even when the score is 100. Emulator executable and config filenames alone are never an auto-move authorization.

Important caveat: `verified_id` in this experiment is an oracle fixture label, **not** a working validation implementation. Obtaining trustworthy offline anchors without excluding standalone games is the core unresolved engineering problem.

## Nine-case policy-level test

Synthetic cases: Unity game with verified ID; Unity game without store ID; forged Unity utility; Unreal-like backup utility; opaque EXE with verified ID; standalone legitimate game; fake emulator binary plus config; known emulator plus config; spoofed store manifest utility.

Baseline readiness derived from the inspected source formula: **4/5 real game-or-emulator positives ready, 4/4 negatives incorrectly ready**. (The five positives are verified Unity game, unverified Unity game, opaque EXE game, standalone game, genuine emulator; opaque and standalone were not ready, so baseline actually **3/5 positives ready**.) Baseline negative cases were all 4/4 ready. Proposed strict identity gate: **2/5 positives ready, 0/4 negatives ready**. These are *toy fixture outcomes only*, not measured precision/recall of production code. No real file moves were attempted. The gate's cost is false negatives for standalone games and emulators; solve with trusted binary fingerprint registries and separate emulator verification, not by relaxing the move authorization.

## Further independent source findings

- `candidates()` walks directories separately from `_walk()`; its `DANGEROUS_PATH_COMPONENTS` does not include `mods`, `tools`, `fix`, or `patch` even though the inventory ignores them. An EXE under a skipped directory can be ranked as a game candidate. Unify scanner inventory and candidate selection.
- `_walk()` may stop at `MAX_FILES` while its returned `bool(queue)` is false. Return explicit `hit_limit` and refuse automatic moves on incomplete inventories.
- `scan_downloads()` sorts alphabetically and truncates to 200. New downloads can be starved. Switch to persistent cursor/change journal or newest-first with full reconciliation.
- `move_verified()` calls `os.rename` after a target existence check. A check-then-rename race must be tested on Windows/NTFS; do not claim no-overwrite atomicity without platform-specific tests. Keep a journal and rollback plan.
- Product identity and edition are different entities. Artwork should be joined by canonical `(product_id, platform, edition_id)` rather than a cleaned title string, with per-asset provenance and review of ambiguous sequels/remasters.
