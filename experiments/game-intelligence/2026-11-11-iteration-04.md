## New hypothesis: alphabetical starvation
If more than 200 entries are in Downloads, a game whose name sorts after the first 200 entries may *never* be inspected, regardless of age or how often the scan is repeated. This is a completeness and recall problem independent of the 1,800-file per-folder bug from iteration 3.

## Reproduction
Created a disposable temporary directory with 200 files named `A_000_unrelated.txt` ... `A_199_unrelated.txt` and one synthetic `Z_Outer_Wilds` game directory containing inert text placeholders `OuterWilds.exe` and `UnityPlayer.dll`. No real binary executed or moved. Applied production's alphabetical top-200 selection and an alternative recency-priority top-200 selection.

Results:
- Total entries: 201.
- Current alphabetical selection contains the game: **false**.
- Recency-priority selection contains the game: **true** in this fixture.
- Both bounded selections omit one entry; recency ordering alone is NOT a complete solution.
- Repeating the unchanged alphabetical scan indefinitely cannot discover the game; no empirical game-identity precision/recall was measured beyond candidate-selection coverage in this fixture.

## Proposed durable fix: resumable inventory and explicit completeness
Separate enumeration from inspection. Maintain a persistent cursor/checkpoint over stable file identities, process a bounded batch each pass, and rotate across all candidates fairly. Track `inventory_status` as `complete`, `partial`, or `error` and report `remaining` or `unknown`. Rescan changes and new arrivals promptly, but ensure no permanent starvation for old entries. Sorting by mtime is a useful fast path only, not a replacement for exhaustive coverage. On Windows, avoid depending on filename alone for cursor validity: entries may be renamed/deleted between passes; maintain a generation/snapshot strategy or change journal where available.

Avoid treating absence from a partial scan as absence from the user's library. The same applies to emulator directories.
