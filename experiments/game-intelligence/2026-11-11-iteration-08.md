## Hypothesis and method
A SQLite intent journal reconciled against actual source/destination state can recover from crashes on either side of a same-volume rename without blindly repeating the move.

Executed a disposable Python experiment using actual `sqlite3` on-disk database and `os.rename` between temporary Downloads/Games directories, with synthetic data only. Five independent fresh temporary environments tested simulated crash before intent, after intent, after rename before completion, after completion, and no crash. Restarted SQLite and reconciled paths. Separately tested an already existing destination.

## Observed outcomes
| Injection point | Post-restart state | Original file copies |
|---|---|---:|
| Before intent commit | No intent, source intact | 1 |
| After intent commit | Planned, source intact; requires revalidation | 1 |
| After rename, before completion | Destination intact; journal recovered | 1 |
| After completion | Destination intact; journal verified | 1 |
| No crash | Destination intact; journal verified | 1 |

Destination-exists fixture was blocked by preflight, leaving source and destination data intact. Five of five simple crash scenarios retained exactly one original copy. This **does not** prove exactly-once moves under concurrency or Windows behavior.

## Important new failure modes
1. The current `if target.exists(): ... os.rename(src,target)` is a check-then-act race. On POSIX, a concurrently created empty destination directory may be replaced by `os.rename`. On Windows the call commonly fails if destination exists, but application safety must not rely on platform accident. Require a destination reservation or no-replace primitive, and reject any ambiguous state.
2. A moved destination may be a replacement or tampered folder; mere existence is insufficient to reconcile. Persist volume/file identity and bounded content fingerprints **before** the rename and verify on restart. Never infer success from path alone.
3. Current `_walk` excludes IGNORE_DIRS and can incorrectly report a complete inventory; safety traversal must be independent of recognition.
4. A crash after renaming but before persisting a journal outcome can be recovered if and only if the source/destination identity is verified.
5. Leased workers need generation fencing and an operation-specific exclusive lock; idempotent SQL results alone do not prevent two workers from attempting the same move.

## Proposed durable protocol
A) Validate full safety inventory and canonical identity; B) obtain exclusive operation lock and record a durable `planned` intent including src, dst, expected file ID, fingerprint and generation; C) revalidate under lock, use a no-overwrite same-volume move; D) verify destination identity; E) commit `verified` journal entry; F) on startup reconcile `planned` or `moving` by examining source, destination and recorded identity. If ambiguous, quarantine job for manual review, never blind retry.
