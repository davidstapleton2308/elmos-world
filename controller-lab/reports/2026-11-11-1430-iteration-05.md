## Finding
In `command_emulate`'s `finally` block, sending the neutral keyboard/mouse/gamepad state and requesting virtual-device destruction shared one `try` block. If a neutral send raised (broken pipe, bridge failure), the destroy request for that slot was skipped. This could leave the slot live while the bridge still responds to subsequent requests.

## Changes
- `b9ae9a85371decd254f04832400cb8f475eef355`: separate neutralization and destruction attempts for each created slot; log independent warnings. Destruction is attempted even when the neutral report fails.
- `bcd57271a5a8d055c2c2a22bd7cc29fd0494835a`: add AST regression test asserting distinct cleanup `try` blocks and a destroy request in the second block.

## Technical rationale
Windows driver surprise removal requires failure-tolerant cleanup and bounded I/O. Microsoft guidance: https://learn.microsoft.com/en-us/windows-hardware/drivers/wdf/surprise-removal-sequence . A neutral state is a best-effort input release, while destruction is a separate fallback. Neither guarantees cleanup if the bridge process itself has failed.
