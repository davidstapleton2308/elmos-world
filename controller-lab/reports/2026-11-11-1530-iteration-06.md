## Problem and design
A Python client can freeze, deadlock, lose its reader, or stop producing input without executing its `finally` cleanup. Its bridge process may remain alive with buttons held indefinitely. Client-side neutralization cannot solve this failure mode.

Add a bridge-owned, per-slot input lease: when a virtual slot is created or successfully receives a state, keyboard, or mouse report, record `Stopwatch.GetTimestamp()`. Every 250 ms check for elapsed monotonic time >= 3 seconds. Expire the slot by removing it from the dictionaries and disposing its virtual device, then emit `watchdog_expired`. All controller operations and the timer callback use the same `DeviceLock` to prevent concurrent dictionary access and disposal during submission. A wall-clock adjustment cannot extend a lease.

This deliberately **destroys** the stale slot rather than submitting a neutral state, because destruction is the fallback already used by shutdown. A client resuming after 3 seconds must explicitly recreate its slot. The 3-second threshold is a provisional safety policy, not an empirically tuned value.
